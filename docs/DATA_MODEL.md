# Conceptual D1 data model

Status: conceptual only. No migration exists. Implement only the tables needed by the current phase.

## Modeling rules

- Mercado Libre remains operational source of truth.
- Store app configuration, encrypted credentials, safety/audit state, minimal order facts, and historical observations—not a full upstream mirror.
- Use UTC timestamps and explicit `captured_at`/`last_synced_at` fields.
- Store money as integer minor units plus ISO currency code.
- Use opaque text IDs generated by the application; never expose sequential database IDs as authorization.
- Keep frequently queried fields as columns. Use JSON only for bounded, versioned details that do not need relational filtering.
- Exclude buyer addresses, messages, tax data, and other PII unless a later approved use case and retention policy requires them.
- Never store plaintext access/refresh tokens or object binaries in D1.

## Phase 1 tables

### `accounts`

One connected seller initially.

- `id` text primary key
- `ml_user_id` text unique
- `site_id` text, constrained by application to `MPE`
- `nickname` text nullable
- `connection_status` text
- `connected_at`, `last_verified_at`, `created_at`, `updated_at` UTC text

Do not store profile fields that are not needed for account identification.

### `oauth_credentials`

One current rotating token pair per account.

- `account_id` primary/foreign key
- `access_ciphertext`, `access_iv`
- `refresh_ciphertext`, `refresh_iv`
- `expires_at`
- `token_type`, `scope`
- `key_version`
- `credential_version` integer for compare-and-swap
- `refresh_lease_until`, `refresh_lease_owner` nullable
- `updated_at`

Ciphertexts are authenticated AES-GCM values. The encryption key is a Worker Secret, never a D1 value.

### `oauth_states`

Short-lived OAuth transaction state.

- `state_hash` primary key
- encrypted PKCE verifier and IV
- `safe_return_path`
- `expires_at`, `consumed_at`, `created_at`

Delete expired/consumed rows on a bounded schedule. Never persist the authorization code.

### `audit_events`

Append-only security and operational audit trail.

- `id` primary key
- `account_id` nullable for pre-connection events
- `actor_ref` redacted/stable owner reference
- `action`, `resource_type`, `resource_id`
- `intent_id` nullable
- `outcome`, `error_code`, `warning_codes_json`
- `before_json`, `after_json` redacted and bounded
- `upstream_status`, `upstream_request_id`
- `correlation_id`, `created_at`

Phase 1 uses this for connect, refresh, reconnect, and security events. Later phases attach listing mutations.

## Tables introduced only when their phase needs them

### `change_intents` — Phase 3

- action/resource/account and single-use status
- canonical redacted `before_json` and `proposed_json`
- precondition hash and upstream observation time
- expiry, confirmation, apply, rejection, and failure timestamps
- idempotency/correlation reference

Allowed states: `pending`, `confirmed`, `applying`, `applied`, `rejected`, `expired`, `stale`, `failed`. State transitions are transactional and fail closed.

### `webhook_events` — when notifications are enabled

- deduplication key, application/user/topic/resource reference
- sent/received time
- `pending`, `processing`, `processed`, or `failed` state
- attempt count, next attempt, sanitized last error

Unique constraints make duplicate delivery harmless. The row contains a reference, not authoritative listing/order state.

### `sync_cursors` — first history/reconciliation job

- job/account key
- cursor or watermark
- lease fields
- last success, next run, sanitized error, attempt count

### `listing_snapshots` — analytics/history phase

- account/item/capture time
- status, substatus, condition
- price in minor units/currency
- owner-visible available quantity
- visits total and documented counters used by metrics
- source observation/request time

Unique `(account_id, item_id, captured_at)` and indexes by item/time and account/time. Use deltas carefully for relisted visit chains.

### `order_facts` — sales phase

Minimal non-PII facts needed for reconciliation/history:

- account/order/item identifiers
- created/closed/last-synced time
- order/payment status and optional shipment status
- quantity, unit amount, line/total amount, currency

Define an update/upsert strategy because order status changes. Do not persist buyer contact, address, payment credential, or full upstream JSON. Retention remains an explicit decision.

### `comparable_sets` and `comparable_entries` — market phase

`comparable_sets` stores source item, capture time, condition, algorithm version, normalized query criteria, count, min/max/mean/median/percentiles, and owner-review state.

`comparable_entries` stores the observed candidate ID/product ID, title/permalink required for inspection, category, condition, price/currency, normalized structured identifiers, scores, inclusion state/reason, and observation time.

Statistics are reproducible from entries. Never store only an opaque aggregate.

### `ai_suggestions` — AI text phase

Store suggestion kind, source fingerprint, provider/model identifier, bounded grounded inputs/proposal, decision, and applied audit reference. Retention and sensitive-data policy must be approved before implementation.

### `image_assets` — image phase

Store metadata and private R2 keys for original/proposal, content hash, transform/provenance, owner decision, and applied audit reference. Image bytes live in R2, not D1. Original objects are immutable.

## Index and volume guidance

- Add indexes only for demonstrated access paths: account/status, resource/time, job state/time, and unique upstream IDs.
- Snapshot jobs should batch inserts and avoid full-table scans.
- Retention/aggregation should be reversible and documented before deleting raw observations.
- D1's single-writer behavior is acceptable for this personal scale; serialize credential refresh and bounded jobs intentionally.

## Not in the database

- Mercado Libre passwords or plaintext tokens
- a complete listing/order/customer mirror
- image binaries
- arbitrary API response dumps
- unrestricted AI transcripts
- buyer PII without a separately approved requirement
- provider secrets
